# ИИ-агент «Анализ организационной структуры и функционала» — текущий план и приёмка

Задача 1, владелец — Казахтелеком. Оригинальные ТЗ и критерии сохранены дословно в Appendix A/B. Ниже — состояние реализации, а не обещание баллов жюри. История выполненных этапов — `docs/CHANGELOG.md`.

## 0. Статус и приоритет

Основной конвейер и API реализованы: Word/PDF/Excel → подразделения → функции → сопоставления → наблюдения с цитатами → заключение. Контрольные PDF поставляются в образе backend. Проверки выполняются в Docker. UI сейчас не расширяем.

Оставшийся обязательный организационный пункт: команда должна передать жюри отдельную ограниченную учётную конфигурацию модели приватно. Работающий публичный сервер и ключ команды не доказывают прохождение этого требования. До передачи конфигурации K3 остаётся частичным.

## 1. Система

Один `docker-compose.yml`: Caddy → Vue 3/Vite 6 frontend и Node 22/Express 5 backend; backend → Python 3.12/FastAPI extractor, MongoDB 8 и OpenAI-совместимый API. Только Caddy публикует порты. Модель, адрес и ключ задаются через env; новых сервисов не требуется. `analyses` хранит состояние, разобранные пункты и результаты; `users` — демо/пользовательские аккаунты; `regulatory_norms` — нормативный корпус.

## 2. Основной сценарий

1. Пользователь загружает комплекты «до» и «после» либо запускает комплект через `POST /api/analyses/demo`.
2. API отвечает `202 {analysis_id}`. UI опрашивает `GET /api/analyses/:id`.
3. Фоновые этапы: `clauses` → `structure` → `functions` → `compare` → `report`; результат получает `done` либо понятную ошибку `failed`.
4. Пользователь проверяет подразделения, возможные потери/дублирование/конфликты, исходные пункты и заключение. Все выводы рекомендательные.
5. После перезапуска незавершённые задания получают `interrupted`, а не остаются в бесконечном ожидании. История запусков доступна для вошедшего пользователя; API основного анализа открыт для проверки без аккаунта.

## 3. Входные данные

- Bundled PDF: `services/backend/demo/before/redakciya_8.pdf` и `demo/after/redakciya_9.pdf`. Это предоставленные пользователем обезличенные документы, не готовые ответы модели. Происхождение и SHA-256 — в README.
- Extractor поддерживает `.docx`, PDF с текстом, `.xlsx`, `.xlsm`, `.xls`; OCR и старый `.doc` не реализованы.
- Ненумерованные фрагменты, строки Word-таблиц и Excel сохраняют ссылки. Оглавление пропускается без удаления следующих приложений. Обрыв/неполное извлечение останавливает анализ.
- Классификатор входа отклоняет документы, не относящиеся к подразделениям/функциям; его отказ сам по себе не блокирует дальнейшую проверку. Это эвристика, а не гарантия распознавания тематики.

## 4. Модули и Must-have

- **M1:** `structure.js` извлекает подразделения и проверяет источник; код сравнивает ключи. Преемственность оценивается по структуре и обязанностям обеих сторон. Пропущенный, повторный или невалидный ответ — `structure_incomplete`, а не упразднение. Возможная реорганизация не означает юридическое правопреемство.
- **M2:** `extract.js` размечает обязанности и исполнителей; `compare.js` сопоставляет функции. Частичная утрата сохраняет обе цитаты, включая случай смены исполнителя. Ноль функций «до» — `no_functions`.
- **M3:** `compare.js` находит дублирование, общую/частную норму и кандидатов конфликта исполнения аудита с контролем его качества. Неполная оценка конфликта оставляет видимого кандидата `unreviewed`, а не чистый результат. Другие виды конфликтов отдельными правилами не покрыты.
- **M4:** цитата проверяется по `(doc_id, clause_id, side)`, с точной пунктуацией и регистром, допускаются различия пробелов. Повторяющиеся номера в разных файлах не подавляют поиск дублирования. Заключение содержит ID документов и имена файлов.
- **M5:** `report.js` строит заключение кодом из проверенных записей и источников подразделений. Дополнительного свободного ответа модели нет; все находки включены, неверный источник даёт `report_unverified`. Рекомендации — действия по проверке наблюдений, не автоматическое проектирование оргструктуры.

## 5. Сопоставление и ограничения точности

Полное нормализованное совпадение исходного текста проходит без судьи. Иначе лексика/эмбеддинги отбирают до трёх кандидатов, модель оценивает смысл с учётом отрицаний, сроков и объёма обязанности. Слабое положительное соответствие остаётся частичным. Сбой, неуверенное отсутствие, пропущенный/повторный ID или посторонний кандидат останавливает сравнение (`comparison_incomplete`). Дублирование использует пороги сходства и дополнительную оценку пограничных пар; это поиск кандидатов, не доказательство избыточности.

Ограничения: одно лучшее соответствие на функцию; разбиение обязанности между несколькими пунктами может выглядеть как частичная потеря. Отбор кандидатов и модель могут ошибаться; точность на произвольных документах не измерена. Без эмбеддингов работает лексический запасной путь. Контекст структуры ограничен 24 000 символов, контекст преемственности — 48 000 на сторону; за раз оцениваются до 100 пограничных пар дублирования и до 3 пар конфликта на исполнителя. Ограничения требуют ручной проверки полноты.

## 6. Данные результата

Источником контракта являются `services/backend/src/schemas.js` и `pipeline/clauses.js`: `documents`, `units`, `unit_changes`, `functions.before/after`, `matches`, `findings`, `regulatory`, `conclusion_md`, `stats`. Один документ Mongo на запуск. Цитаты и численные сводки строятся кодом; модель не задаёт итоговые количества. Загруженные файлы не сохраняются, их извлечённый текст остаётся в анализе.

## 7. API

- `POST /api/analyses`: multipart `before`, `after`, необязательное `regulations`; до 10 файлов на поле и лимит `MAX_UPLOAD_MB`.
- `POST /api/analyses/demo`: тот же конвейер на встроенных PDF, без сохранённых ответов.
- `GET /api/analyses/:id`: состояние и результат.
- `GET /api/analyses`: история текущего пользователя, требует сессию.
- `POST /api/documents/extract`: отдельная проверка парсера.
- `/api/health`, `/api/auth/*`: состояние и демо-доступ. Ошибки имеют `error.code/message`.

## 8. Отказы и надёжность

Проверяются тип, размер и наличие файлов; внешний вызов ограничен таймаутом/повторами; ответы модели валидируются схемами. Неполные документы, сравнения и источники не должны становиться «всё в порядке». O1 необязателен: его отказ отражён в `stats.regulatory_status` и не доказывает соответствия законодательству. Секреты остаются вне Git и frontend.

## 9. Контрольный комплект и ожидаемая проверка

- M1: созданы ДИТААД и ДОА; сохранены ДНМ и ДККМ; бывшее направление внутреннего аудита сопоставлено как минимум с ДИТААД и ДОА.
- M2: возможная потеря права формировать группы контроля качества — «до», п. 5.6.2, с исходной цитатой. Пункт 5.7.2 может быть частичным соответствием, а не полной потерей.
- M3: возможное дублирование «после» 5.4.3 / 5.5.8; возможный конфликт ДККМ с нормой контроля качества 5.5.2.
- M4: каждый источник реально существует на правильной стороне; текст цитаты входит в конкретный пункт.
- M5: заключение включает все находки и корректные ссылки; числа совпадают с записями результата.

`scripts/verify-control.py` проверяет эти условия в HTTP smoke. Дополнительные находки и формулировки модели могут меняться; ранее встречались расхождения в реорганизации и дублировании. Контрольный комплект не является оценкой полноты на всех документах.

## 10. Приёмка в Docker

```bash
docker compose up --build -d --wait
docker compose run --rm --no-deps backend node --test
docker compose run --rm --no-deps extractor pytest -q
./scripts/formats-test.sh
./scripts/smoke.sh --require-analysis
./scripts/clean-test.sh --env-file /absolute/path/reviewer.env
```

Форматные тесты создают реальные DOCX (абзацы и таблицы), PDF, XLSX и смешанный комплект; настоящий extractor и весь конвейер проверяются с тестовым классификатором вместо платной модели. Основной API заглушек не использует. Негативные регрессии: сбой/неполный ответ, отрицание и сужение обязанности, неверные цитаты/стороны, одинаковая нумерация в разных файлах, приложение после оглавления, отсутствие исходных функций, неподтверждённый отчёт.

`clean-test.sh` клонирует только коммиты, собирает без кеша, использует изолированную MongoDB и требует успешного основного сценария. `--infrastructure-only` отдельно проверяет запуск с `.env.example` и явно НЕ подтверждает AI-сценарий. Не помещать ключ в `.env.example`.

## Appendix A. Original ТЗ (verbatim)

1. ИИ-агент «Анализ организационной структуры и функционала»
Цель: разработать прототип ИИ-агента, который сравнивает организационные и функциональные документы, выявляет возможную потерю или дублирование функций и формирует объяснимое заключение со ссылками на исходные документы.

2. Проблема
При реорганизации подразделений необходимо вручную сопоставлять организационные структуры, положения и другие приложения к распорядительным документам.
Основные риски: потеря функций, дублирование функционала, пересечение зон ответственности и потенциальный конфликт интересов. Дополнительно может потребоваться проверка соответствия функций внешним требованиям и сравнение структуры с практикой других операторов.

3. Пользователь и сценарий
Основной пользователь – сотрудник подразделения, проводящий анализ организационных изменений.
Сценарий: пользователь загружает комплект документов «до» и «после» реорганизации – агент определяет изменённые подразделения – сравнивает их функции – показывает выявленные отклонения и источники – формирует итоговое заключение.

4. Задача
Разработать прототип ИИ-агента для интеллектуального сопоставления организационных структур и функционала подразделений с возможностью выявления отклонений и формирования объяснимых выводов.

5. Вход → выход
Вход: организационные структуры, положения о структурных подразделениях, должностные инструкции, распорядительные документы и приложения к ним, внутренние нормативные документы. Форматы: Word, PDF, Excel.
Выход: перечень преобразованных/сохранённых подразделений, таблица сопоставления функций, выявленные потери и дублирования, потенциальные конфликты интересов, ссылки на подтверждающие пункты документов и краткие рекомендации.

6. Данные
Организатор предоставляет тестовый набор документов для сравнения. Для проверки соответствия внешним требованиям дополнительно могут быть предоставлены конкретные нормативные документы, стандарты и требования, которыми руководствуются подразделения.
При наличии возможности для бенчмаркинга предоставляются открытые данные об организационных структурах других операторов. Объём и способ доступа к данным указываются организатором отдельно.

7. Must have
1) Определить по приложениям, какие структурные подразделения были реорганизованы, какие сохранились и какие созданы.
2) Сопоставить функционал преобразованных и существующих подразделений и выявить потенциальную потерю функций.
3) Сопоставить функционал подразделений между собой и выявить возможное дублирование функций и конфликт интересов.
4) Для каждого вывода показать подтверждающий источник: документ и соответствующий фрагмент/пункт.
5) Сформировать итоговое аналитическое заключение в понятном для пользователя виде.

8. Опционально
1) Сопоставление задач и функций подразделений с предоставленным законодательством, стандартами и регуляторными требованиями.
2) Сравнение организационных структур преобразованных/созданных департаментов с организационными структурами других операторов.
3) Формирование рекомендаций по перераспределению функций и устранению выявленных пересечений.

9. Ограничения
Выводы ИИ носят рекомендательный характер и требуют проверки ответственным сотрудником. Агент не должен формировать утверждения, не подтверждённые предоставленными документами. Для каждого существенного вывода должна сохраняться прослеживаемость до источника.

10. Артефакты
Работающий прототип, интерфейс для загрузки документов и просмотра результатов, репозиторий с исходным кодом, README с инструкцией запуска и краткое описание архитектуры решения.

11. Простая проверка решения
Команда демонстрирует решение на контрольном комплекте документов, где заранее известны несколько изменений: реорганизация подразделения, потеря функции и дублирование функционала. Проверяется, обнаружил ли агент эти случаи и указал ли корректные источники.
